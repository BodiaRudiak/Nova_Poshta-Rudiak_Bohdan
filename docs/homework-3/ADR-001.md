# ADR-001. Зберігання поточного статусу посилки разом з історією змін

**Статус:** Прийнято для навчальної архітектури.

## 1.1. Контекст і проблема

Однією з основних функцій системи «Нова пошта» є відстеження посилок.

Користувач повинен у будь-який момент дізнатися, де знаходиться його відправлення та який воно має статус. Наприклад:

1. Створено накладну.
2. Посилку прийнято у відділенні.
3. Посилка проходить сортування.
4. Посилка перебуває в дорозі.
5. Посилка прибула у відділення.
6. Посилку отримано.

При цьому недостатньо зберігати тільки останній статус. Іноді потрібно знати, коли саме посилка проходила певний етап, хто змінив інформацію та чи були затримки.

Наприклад, клієнт звернувся до служби підтримки зі скаргою, що його посилка три дні перебувала в дорозі. Якщо система зберігає тільки поточний статус «Прибуло у відділення», працівник не зможе повноцінно перевірити історію переміщення.

Отже, виникає архітектурне питання: **як зберігати інформацію про стан посилки, щоб одночасно забезпечити швидке відстеження та можливість перевірки попередніх операцій?**

## 1.2. Розглянуті альтернативи

### Варіант 1. Зберігати тільки поточний статус

У базі даних для кожної посилки зберігається один актуальний статус, який змінюється під час проходження етапів доставки.

**Переваги:**

- Проста структура бази даних.
- Швидке отримання актуального статусу.
- Менший обсяг даних.

**Недоліки:**

- Відсутня повна історія переміщення.
- Складніше розбирати скарги клієнтів.
- Неможливо визначити, коли саме відбувалася попередня зміна, якщо ці дані більше ніде не зберігаються.

Цей варіант підійшов би для простої системи, де важливий тільки поточний результат, але для служби доставки його можливостей недостатньо.

### Варіант 2. Зберігати поточний статус та окрему історію змін

У системі створюються дві логічні структури даних.

Перша зберігає основну інформацію про посилку та її актуальний статус.

Друга зберігає записи про зміни статусів: попередній стан, новий стан, час зміни та джерело операції.

**Переваги:**

- Швидкий доступ до актуального статусу.
- Збереження історії доставки.
- Можливість аналізувати затримки та помилки.
- Відносно проста реалізація.

**Недоліки:**

- Потрібно підтримувати узгодженість двох структур.
- Збільшується обсяг даних.
- Необхідно правильно обробляти повторні й затримані події.

### Варіант 3. Event Sourcing

Event Sourcing — підхід, у якому головним джерелом інформації є послідовність подій, що відбулися із системою.

Наприклад, замість безпосереднього оновлення статусу ми зберігаємо всі події: посилку створено, прийнято, відсортовано, передано кур'єру тощо. На основі цих подій обчислюється поточний стан.

**Переваги:**

- Детальна історія подій.
- Можливість відновлювати стан системи на певний момент часу.
- Можливість повторно обробляти події.

**Недоліки:**

- Складніша архітектура.
- Потрібно контролювати порядок і повторну обробку подій.
- Зміна правил обробки може впливати на відновлення старих станів.
- Може знадобитися окреме представлення поточного стану для швидкого читання.

Цей підхід доцільний, якщо повне відновлення стану з подій є важливою вимогою. Для нашого навчального проєкту така складність поки що не виправдана.

## 1.3. Прийняте рішення

**Обираємо другий варіант — зберігання поточного статусу посилки разом з окремою історією змін.**

Для цього використовуємо PostgreSQL.

У таблиці посилок зберігаються основні дані, унікальний номер накладної, поточний статус та версія запису, яка використовується для захисту від одночасних змін.

Окрема таблиця історії містить інформацію про кожну підтверджену зміну статусу:

- попередній і новий статус;
- фактичний час операції (`occurred_at`) і час запису в систему (`recorded_at`);
- джерело операції (відділення, сортувальний центр, кур'єр, інтеграція) та виконавця;
- унікальний ідентифікатор операції, який захищає від повторного запису тієї самої події;
- позначку «запізніла подія», якщо подія записана в історію, але не змінила поточний статус.

Розділення фактичного часу операції та часу запису потрібне, бо події можуть надходити із запізненням, наприклад після відновлення зв'язку у відділенні.

Оновлення поточного стану й додавання запису до історії повинні відбуватися в межах однієї транзакції. Це означає, що обидві операції або завершуються успішно, або скасовуються разом.

## 1.4. Як це працюватиме

Наприклад, оператор прийняв посилку у відділенні.

1. Оператор сканує номер накладної.
2. Backend API отримує запит.
3. Компонент «Статуси та історія» перевіряє, чи дозволена операція.
4. У базі даних змінюється поточний статус посилки.
5. У тій самій транзакції до історії додається запис про зміну.
6. Після успішного завершення транзакції новий статус стає доступним користувачу.

Якщо під час збереження виникла помилка, система не повинна залишити новий поточний статус без відповідного запису в історії.

## 1.5. Чому обрано саме це рішення

Для користувача найважливіше швидко отримувати актуальну інформацію про доставку.

Для працівників і служби підтримки важливо мати можливість переглядати попередні події.

Другий варіант дозволяє задовольнити обидві потреби без впровадження складної архітектури Event Sourcing.

## 1.6. Наслідки рішення

**Позитивні наслідки:**

1. Користувач швидко отримує актуальний статус.
2. Працівники можуть перевіряти історію переміщення.
3. Система отримує можливість аналізувати затримки.
4. Історія допомагає розглядати скарги та спірні ситуації.
5. Архітектура залишається відносно простою.

**Негативні наслідки:**

1. Потрібно підтримувати дві пов'язані структури даних.
2. Кожна зміна статусу потребує додаткового запису.
3. Зі збільшенням кількості посилок таблиця історії може стати дуже великою.
4. Потрібно контролювати цілісність даних та повторні події.
5. Історія статусів не обов'язково містить усю інформацію, необхідну для повного відновлення стану системи.

## 1.7. Рівень впевненості

**Високий.**

Це рішення забезпечує потрібний баланс між швидкодією, збереженням історії та складністю реалізації.

Водночас конкретну продуктивність потрібно перевірити під навантаженням.

## 1.8. Коли рішення потрібно переглянути

Рішення варто переглянути, якщо:

1. З'явиться вимога повністю відновлювати стан системи за історичними подіями.
2. Історія буде використовуватися для складної аналітики та повторного відтворення бізнес-процесів.
3. Обсяг записів або навантаження призведуть до того, що час відповіді на запит відстеження перевищить 300 мс (p95).
