# ADR-003. Надійне асинхронне надсилання сповіщень через Notification Worker

**Статус:** Прийнято для навчальної архітектури.

## 3.1. Контекст і проблема

Система «Нова пошта» повинна повідомляти клієнтів про важливі зміни, пов'язані з доставкою. Наприклад:

1. Створено відправлення.
2. Посилку прийнято.
3. Посилка прибула у відділення.
4. Посилку передано кур'єру.
5. Доставку завершено.
6. Виникла затримка або інша проблема.

Для цього система використовує зовнішні сервіси SMS, push-повідомлень та електронної пошти.

Однак зовнішні сервіси можуть працювати повільно, тимчасово бути недоступними або повертати помилки.

Виникає архітектурне питання: **чи повинна основна операція з посилкою залежати від успішного надсилання повідомлення?**

Наприклад, працівник відділення змінює статус посилки на «Прибуло у відділення». У цей момент SMS-сервіс недоступний.

Якщо надсилання повідомлення є обов'язковою частиною основної операції, система може затримати відповідь працівнику або помилково повідомити про невдалу зміну статусу.

При цьому фактичне прибуття посилки ніяк не залежить від роботи SMS-сервісу.

Отже, потрібно розділити основну операцію та процес надсилання повідомлення, не допускаючи втрати самого завдання на сповіщення.

## 3.2. Розглянуті альтернативи

### Варіант 1. Надсилати повідомлення безпосередньо з Backend API

Після зміни статусу Backend API звертається до зовнішнього сервісу та очікує результату.

**Переваги:**

- Проста реалізація.
- Не потрібно створювати додатковий процес.
- Легко зрозуміти послідовність виконання.

**Недоліки:**

- Повільна робота зовнішнього сервісу збільшує час відповіді.
- Тимчасова недоступність сервісу створює проблеми для основної операції.
- Складніше незалежно керувати повторними спробами.

### Варіант 2. Надсилати повідомлення у фоновому режимі без збереження завдання

Backend API запускає операцію надсилання, але не очікує її завершення.

**Переваги:**

- Швидка відповідь користувачу.
- Невелика складність реалізації.
- Немає необхідності чекати зовнішній сервіс.

**Недоліки:**

- Якщо сервер завершить роботу, завдання може загубитися.
- Складно відстежувати невдалі повідомлення.
- Відсутня надійна система повторних спроб.

### Варіант 3. Використовувати Notification Worker і транзакційний Outbox

Backend API створює завдання на сповіщення та зберігає його в PostgreSQL.

Окремий Notification Worker періодично перевіряє нові завдання та надсилає повідомлення через зовнішній сервіс.

Для надійності використовується підхід **Transactional Outbox**.

**Переваги:**

- Основна операція не залежить від швидкості SMS або email.
- Завдання зберігаються в базі даних.
- Можна повторювати невдалі спроби.
- Можна відстежувати стан надсилання.

**Недоліки:**

- Потрібно розробити та підтримувати додатковий процес.
- Потрібно контролювати чергу повідомлень.
- Повідомлення можуть надходити із затримкою.
- Потрібно захищатися від повторного надсилання.

## 3.3. Прийняте рішення

**Обираємо третій варіант — Notification Worker разом із Transactional Outbox.**

У запропонованій архітектурі:

1. Backend API обробляє зміну статусу посилки.
2. У PostgreSQL зберігається новий статус і запис в історії.
3. У межах тієї самої транзакції компонент Outbox створює завдання на сповіщення.
4. Notification Worker окремо знаходить нове завдання.
5. Worker звертається до SMS, push або email-провайдера.
6. Після підтвердження надсилання Worker оновлює стан завдання.

Якщо транзакція зміни статусу не завершилася, завдання на сповіщення також не зберігається.

Якщо транзакція завершилася успішно, завдання залишається в базі навіть після перезапуску Backend API.

## 3.4. Як це працюватиме

Наприклад, посилка прибула у відділення.

**Крок 1.** Працівник сканує посилку.

**Крок 2.** Backend API отримує запит і перевіряє його.

**Крок 3.** Компонент статусів змінює стан відправлення.

**Крок 4.** У тій самій транзакції створюється завдання на повідомлення клієнта.

**Крок 5.** Основна операція успішно завершується.

**Крок 6.** Notification Worker зчитує завдання та надсилає його зовнішньому сервісу.

**Крок 7.** Якщо сервіс підтвердив прийняття повідомлення, завдання позначається як оброблене.

У випадку тимчасової помилки Worker зберігає інформацію про невдалу спробу та повторює надсилання з експоненційною затримкою: 30 с, 2 хв, 10 хв, 30 хв, далі щогодини, загалом до 24 годин. Після вичерпання спроб завдання переводиться у стан «Не доставлено», який потребує перевірки або окремої обробки.

## 3.5. Що відбуватиметься під час збоїв

**Ситуація 1. Недоступний SMS-сервіс**

Статус посилки вже збережено.

Notification Worker фіксує помилку та повторює спробу відповідно до встановлених правил. Якщо в користувача є інший канал (push або email), повідомлення може бути надіслане через нього.

Основна робота системи продовжується.

**Ситуація 2. Backend API перезапустився після зміни статусу**

Якщо транзакцію завершено, завдання на сповіщення залишається в PostgreSQL.

Notification Worker зможе обробити його пізніше.

**Ситуація 3. Notification Worker аварійно завершив роботу**

Після відновлення Worker продовжує обробку незавершених завдань.

**Ситуація 4. Провайдер прийняв повідомлення, але відповідь не дійшла**

Система може повторити запит, хоча перше повідомлення вже було прийнято провайдером.

Тому для запобігання дублюванню використовуються ідентифікатори операцій та механізми ідемпотентності, якщо їх підтримує провайдер.

Важливо розуміти, що така архітектура не гарантує абсолютної відсутності повторних повідомлень у всіх ситуаціях. Вона забезпечує надійне збереження завдань і контрольовану повторну обробку (доставка «щонайменше один раз»).

## 3.6. Чому обрано саме це рішення

Головне завдання системи доставки — правильно обробити відправлення та зберегти його актуальний стан.

Надсилання повідомлення важливе для клієнта, але воно не повинно блокувати основний процес.

Transactional Outbox дозволяє пов'язати створення завдання на повідомлення зі зміною статусу.

Окремий Notification Worker дозволяє обробляти помилки зовнішніх сервісів незалежно від основного Backend API.

Це забезпечує кращу ізоляцію збоїв та надійність роботи.

## 3.7. Наслідки рішення

**Позитивні наслідки:**

1. Основні операції виконуються без очікування SMS або email.
2. Завдання на сповіщення не губляться при звичайному перезапуску Backend API після успішної транзакції.
3. Система може повторювати невдалі спроби.
4. Можна контролювати кількість необроблених повідомлень.
5. Відмова зовнішнього сервісу не блокує зміну статусу посилки.

**Негативні наслідки:**

1. Потрібно підтримувати окремий Notification Worker.
2. З'являється додаткова таблиця завдань.
3. Необхідно реалізувати контроль повторних спроб.
4. Повідомлення може надходити пізніше за зміну статусу.
5. Потрібно відстежувати накопичення необроблених завдань.
6. За певних збоїв можливе повторне надсилання.
7. Навантаження на PostgreSQL збільшується через операції з outbox.

## 3.8. Рівень впевненості

**Середній.**

Сам підхід добре відповідає вимогам надійності, але конкретну реалізацію потрібно перевірити.

Необхідно протестувати поведінку Worker під час перезапуску, тривалої недоступності зовнішнього сервісу та одночасної обробки великої кількості завдань (ціль — 50 000 завдань за 15 хвилин).

## 3.9. Коли рішення потрібно переглянути

Рішення варто переглянути, якщо:

1. Кількість повідомлень значно збільшиться.
2. PostgreSQL почне відчувати надмірне навантаження через outbox.
3. Черга повідомлень буде регулярно накопичуватися (наприклад, понад 1000 завдань, старших за 5 хвилин, частіше ніж раз на тиждень).
4. З'явиться потреба у складнішій маршрутизації повідомлень.
5. Окрема система черг, наприклад RabbitMQ, стане виправданою з погляду продуктивності та експлуатації.

При цьому перехід на брокер повідомлень не обов'язково означає відмову від Transactional Outbox. Ці механізми можуть використовуватися разом.
