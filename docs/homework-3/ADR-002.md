# ADR-002. Контроль переходів статусів та захист від одночасних змін

**Статус:** Прийнято для навчальної архітектури.

## 2.1. Контекст і проблема

У системі «Нова пошта» багато операцій можуть відбуватися одночасно.

Наприклад, одну посилку можуть обробляти оператор відділення, працівник сортувального центру, кур'єр або зовнішня система інтеграції (CRM може скасувати накладну, поки оператор приймає цю посилку).

Проблема виникає, коли два джерела майже одночасно намагаються змінити інформацію про одну посилку.

Розглянемо ситуацію:

1. Посилка має статус «У дорозі».
2. Працівник сортувального центру отримує інформацію про її прибуття.
3. Одночасно інше джерело надсилає запізнілий запис про попередній етап доставки (наприклад, скан із пристрою, який був без зв'язку).
4. Якщо система некоректно обробить ці два запити, актуальний статус може бути перезаписаний застарілим.

Користувач у такому випадку побачить неправильну інформацію.

Ключовий інваріант системи: **життєвий цикл посилки не повинен повертатися на попередній етап через застарілу або конкурентну операцію.**

Це не означає, що статуси завжди мають числовий порядок. Наприклад, повернення посилки — це окрема дозволена гілка процесу, а не випадкове повернення до попереднього стану.

Отже, потрібно визначити, на якому рівні перевіряти переходи статусів і як захиститися від конкурентних змін.

## 2.2. Розглянуті альтернативи

### Варіант 1. Перевіряти переходи тільки в Backend API

Перед оновленням система перевіряє поточний статус і визначає, чи дозволений новий.

**Переваги:**

- Проста реалізація бізнес-правил.
- Можна повертати користувачу зрозумілі помилки.
- Легко тестувати окремі правила.

**Недоліки:**

- Між перевіркою статусу та його збереженням інший запит може змінити дані.
- Різні процеси можуть отримати застарілу інформацію.
- Прямий запис у базу поза цим компонентом може обійти перевірку.

### Варіант 2. Контролювати переходи тільки на рівні бази даних

Правила дозволених переходів реалізуються безпосередньо в PostgreSQL, наприклад за допомогою спеціальної функції та обмежених прав на зміну статусу.

**Переваги:**

- Єдине місце контролю цілісності.
- Правило застосовується до всіх дозволених записів.
- Легше гарантувати узгодженість при конкурентних операціях.

**Недоліки:**

- Частина бізнес-логіки переноситься в базу даних.
- Складніше формувати деталізовані повідомлення користувачу.
- Зміни правил вимагають уважного керування міграціями.

### Варіант 3. Поєднати перевірку в Backend API та захист на рівні PostgreSQL

Backend API виконує попередню перевірку операції, а база даних забезпечує остаточний контроль зміни.

**Переваги:**

- Користувач отримує зрозумілі повідомлення.
- Дані захищені від конкурентних змін.
- Можна контролювати доступ та цілісність окремо.

**Недоліки:**

- Реалізація складніша.
- Потрібно уникати розбіжностей між правилами.
- Потрібні тести конкурентних операцій.

## 2.3. Прийняте рішення

**Обираємо третій варіант — перевірка в Backend API та захист на рівні PostgreSQL.**

Реалізацію пропонується організувати так:

1. Backend API (компонент «API та RBAC») перевіряє роль користувача та право змінити конкретну посилку.
2. Компонент «Статуси та історія» перевіряє дозволені переходи.
3. Кожен запис посилки має версію, яка збільшується після кожного оновлення.
4. Під час збереження PostgreSQL перевіряє очікувану версію запису.
5. Оновлення виконується лише тоді, коли версія не змінилася з моменту отримання даних.
6. Додаткове правило на рівні бази забороняє недозволені переходи незалежно від того, хто ініціював запит.

Для захисту від одночасного оновлення використовується підхід **Optimistic Locking** — оптимістичне блокування.

Дозволені переходи статусів визначаються єдиним узгодженим набором правил, який використовують і серверна перевірка, і механізм захисту в базі.

## 2.4. Як це працюватиме

Уявімо, що два працівники одночасно відкрили інформацію про посилку.

Обидва отримали запис із версією 5.

Перший працівник виконує дозволену зміну статусу. Система успішно оновлює запис і збільшує версію до 6.

Другий працівник намагається зберегти свою зміну, використовуючи стару версію 5.

База даних виявляє, що запис уже змінився, тому не приймає застаріле оновлення.

Backend API повертає HTTP 409 Conflict з актуальним статусом і версією, а застосунок повідомляє користувачу про конфлікт і пропонує оновити дані.

Таким чином, другий запит не перезаписує результат першого.

Інша ситуація — до системи надходить запізніла подія про старий етап доставки.

Компонент статусів перевіряє дозволений перехід. Якщо подія більше не відповідає поточному стану посилки, вона не змінює актуальний статус, але записується в історію з позначкою «запізніла подія» та фактичним часом операції. Так історія залишається повною, а поточний статус — правильним.

## 2.5. Чому обрано саме це рішення

Для системи доставки правильність статусів важливіша за максимально просту реалізацію.

Помилкове оновлення може вплинути на роботу кур'єра, видачу посилки, сповіщення клієнта або звернення до підтримки.

Перевірка тільки в Backend API не забезпечує достатнього захисту від конкурентних змін.

Водночас перевірка тільки в базі ускладнює взаємодію з користувачем.

Комбінований підхід дозволяє поєднати зручність інтерфейсу з надійним захистом даних.

## 2.6. Наслідки рішення

**Позитивні наслідки:**

1. Захист від перезапису актуальних даних застарілими.
2. Контроль дозволених переходів статусів.
3. Узгоджена робота різних користувачів і процесів.
4. Зрозумілі повідомлення про конфлікти.
5. Зменшення ризику некоректного відстеження посилок.

**Негативні наслідки:**

1. Складніша логіка зміни статусів.
2. Необхідність підтримувати узгоджені правила перевірки.
3. Частина запитів може завершуватися конфліктом версій.
4. Потрібно правильно реалізувати повторні спроби після конфліктів.
5. Необхідні спеціальні тести, які відтворюють одночасні операції.

## 2.7. Рівень впевненості

**Середній.**

Обраний підхід добре вирішує проблему конкурентних змін, але для конкретної системи потрібно перевірити його поведінку під навантаженням.

Особливо важливо визначити частоту конфліктів і вплив перевірок на час виконання операцій (ціль p95 для зміни статусу персоналом — 500 мс).

## 2.8. Коли рішення потрібно переглянути

Рішення варто переглянути, якщо:

1. Кількість одночасних оновлень однієї посилки істотно збільшиться.
2. Часті конфлікти почнуть затримувати обробку відправлень.
3. У системі з'явиться окремий сервіс керування життєвим циклом посилки.
4. Виникне необхідність складнішої координації між кількома незалежними системами.
