# ДЗ-4. Архітектурні характеристики системи «Нова пошта»

## 1. Архітектурні характеристики, важливі для проєкту

Для системи доставки «Нова пошта» я визначив 10 архітектурних характеристик. Вони впливають не лише на якість роботи системи, а й на її структуру: кількість серверів, організацію бази даних, розподіл компонентів і спосіб обробки запитів.

У попередній [C4-моделі](../homework-2/c4-explanations.md) вже передбачено вебзастосунок, мобільний застосунок, Backend API, PostgreSQL та Notification Worker. Тепер потрібно визначити, які додаткові архітектурні механізми необхідні для забезпечення конкретних характеристик.

### 1.1. Data Integrity — цілісність даних

Ця характеристика означає, що інформація про посилки, платежі та статуси повинна залишатися правильною навіть за одночасних операцій або збоїв.

**Як змінюється архітектура:** у нашій схемі вже є PostgreSQL, компонент керування статусами та Outbox. Для підвищення цілісності пропоную додатково передбачити синхронну реплікацію бази даних між зонами доступності.

**Механізми:**

- Транзакції PostgreSQL для спільного збереження статусу, історії та завдання Outbox.
- Optimistic Locking для захисту від одночасного оновлення.
- Синхронне підтвердження запису хоча б однією резервною реплікою.
- Контроль дозволених переходів статусів.
- Ідемпотентність повторних запитів.

Це дозволяє уникати ситуацій, коли користувачу підтвердили зміну статусу, але після відмови основного сервера вона зникла.

### 1.2. Responsiveness — швидкість відповіді

Для клієнта однією з найважливіших функцій є швидке відстеження посилки.

Проблема полягає в тому, що одна система одночасно обробляє нові накладні, платежі, оновлення статусів та велику кількість запитів на відстеження.

**Як змінюється архітектура:** пропоную логічно розділити операції читання та запису.

**Механізми:**

- Основний PostgreSQL приймає зміни статусів і платежів.
- Одна з актуальних реплік бази даних може обслуговувати запити відстеження.
- Backend API використовує окремі маршрути читання та запису.
- Система контролює відставання репліки.
- Якщо репліка відстає понад допустимий час, запит перенаправляється до основної бази.
- Масові партнерські запити обмежуються, щоб вони не блокували відстеження.

Таким чином, високе навантаження на запис менше впливатиме на швидкість отримання інформації клієнтами.

### 1.3. Availability — доступність

Система доставки повинна працювати навіть тоді, коли один сервер або одна зона доступності виходить із ладу.

**Як змінюється архітектура:** замість одного запущеного Backend API пропоную декілька його екземплярів, розміщених у різних зонах доступності.

**Механізми:**

- Балансувальник навантаження перед Backend API.
- Три екземпляри Backend API у трьох зонах доступності.
- PostgreSQL із головним вузлом та двома резервними репліками.
- Автоматичне перемикання на справний вузол бази даних.
- Перевірки працездатності серверів.
- Декілька екземплярів Notification Worker.

Три зони обрано для того, щоб навіть після відмови однієї зони можна було зберегти можливість підтверджувати записи на резервному вузлі.

Це збільшує вартість і складність інфраструктури, але усуває залежність системи від одного сервера.

### 1.4. Scalability — масштабованість

Кількість користувачів і запитів може збільшуватися, наприклад під час свят або масових відправлень інтернет-магазинів.

**Як змінюється архітектура:** потрібно передбачити можливість запускати додаткові екземпляри Backend API та окремо нарощувати ресурси обробки сповіщень.

**Механізми:**

- Горизонтальне масштабування Backend API.
- Балансування запитів між екземплярами.
- Незалежне масштабування Notification Worker.
- Контроль кількості підключень до PostgreSQL.
- Обмеження запитів і черги для пікових навантажень.

Без цих механізмів збільшення кількості користувачів вимагатиме насамперед заміни одного сервера на потужніший.

### 1.5. Security — безпека

Система працює з персональними даними, інформацією про доставки, обліковими записами працівників та платежами.

**Як змінюється архітектура:** у Backend API необхідно зберегти централізовану перевірку прав доступу та ізолювати роботу з конфіденційною інформацією.

**Механізми:**

- RBAC та перевірка доступу до конкретного відправлення.
- HTTPS/TLS для передавання інформації.
- Обов'язкова багатофакторна автентифікація персоналу.
- Перевірка підписів платіжних webhook.
- Захищене зберігання секретів.
- Обмеження доступу до бази даних.

Додаткова архітектурна ізоляція платіжних та адміністративних операцій могла б зменшити наслідки компрометації одного компонента.

### 1.6. Recoverability — відновлюваність

Навіть за наявності резервних серверів можливі масштабні збої, пошкодження даних або помилки адміністраторів.

**Як змінюється архітектура:** потрібно додати окреме резервне сховище та механізми відновлення PostgreSQL.

**Механізми:**

- Регулярні резервні копії.
- Архівування журналів транзакцій WAL.
- Збереження копій поза основною інфраструктурою.
- Перевірка відновлення на тестовому середовищі.
- Можливість відновлення бази на певний момент часу.

Реплікація сама по собі не замінює резервного копіювання, оскільки помилкове видалення даних також може передатися на репліки.

### 1.7. Observability — спостережуваність

Для підтримки системи потрібно швидко визначати, де саме виникла проблема.

**Як змінюється архітектура:** додатково можна передбачити централізовану систему метрик, журналів і трасування запитів.

**Механізми:**

- Збір метрик Backend API та PostgreSQL.
- Моніторинг часу відповіді API.
- Контроль відставання реплік.
- Моніторинг Outbox.
- Централізоване зберігання журналів.
- Сповіщення відповідальних працівників.

Це дозволить швидше знаходити причину затримки доставки даних або відмови окремого компонента.

### 1.8. Interoperability — сумісність із зовнішніми системами

Нова пошта взаємодіє з CRM, інтернет-магазинами та платіжними провайдерами.

**Як змінюється архітектура:** можна виділити окремий рівень адаптерів інтеграцій.

**Механізми:**

- Версіоноване REST API.
- Адаптери для зовнішніх систем.
- Перевірка API-ключів.
- Обробка webhook.
- Перетворення зовнішніх форматів даних у внутрішній формат.

Це зменшує залежність основної бізнес-логіки від особливостей конкретного партнера.

### 1.9. Portability — переносимість

Переносимість визначає, наскільки складно перенести систему до іншого хмарного провайдера або іншого середовища.

**Як змінюється архітектура:** для високої переносимості потрібно використовувати стандартизовані механізми розгортання та мінімізувати залежність від специфічних сервісів провайдера.

**Механізми:**

- Контейнеризація.
- Infrastructure as Code.
- Переносимі конфігурації.
- Уніфікована система секретів.
- Можливість розгортати PostgreSQL і застосунки в іншому середовищі.

Це додає складності під час розробки та підтримки інфраструктури.

### 1.10. Extensibility — розширюваність

У майбутньому можуть з'явитися нові способи доставки, нові платіжні провайдери або канали сповіщень.

**Як змінюється архітектура:** потрібно передбачити окремі інтерфейси та модулі для підключення нових можливостей.

**Механізми:**

- Модульна структура Backend API.
- Інтерфейси для платіжних провайдерів.
- Адаптери SMS, push та email.
- Незалежна конфігурація інтеграцій.
- Тести контрактів між компонентами.

Такий підхід дозволяє розширювати функціональність без повного переписування системи.

### 1.11. Зведення: що кожна характеристика змінює на схемі

Сама назва характеристики («висока доступність») діаграму не змінює. Змінює її лише конкретний механізм. Нижче для кожної характеристики вказано механізм і елемент, який через нього з'являється або змінюється на схемі.

| Характеристика | Механізм | Що змінюється на схемі |
|---|---|---|
| Data Integrity | Синхронна реплікація, транзакції, Optimistic Locking | Level 2: PostgreSQL стає кластером «основний вузол + синхронна репліка» |
| Responsiveness | Розділення читання й запису, контроль відставання репліки | Level 2: окремий зв'язок «Backend API → репліка (читання)». Level 3: компонент статусів ділиться на Tracking Query та Status Command |
| Availability | 3 зони, балансувальник, failover бази | Level 2 / Deployment: новий Load Balancer, Backend API ×3, PostgreSQL 1+2 у трьох зонах, менеджер перемикання |
| Scalability | Горизонтальне масштабування, пул з'єднань, rate limiting | Level 2: Backend API та Notification Worker позначаються як масштабовані (×N). Level 3: компонент обмеження запитів |
| Security | MFA персоналу, перевірка підписів webhook, сховище секретів | Level 2: сховище секретів, доступ до PostgreSQL лише з Backend API. Level 3: окремий ізольований модуль платіжних та адміністративних операцій |
| Recoverability | Резервні копії, архів WAL, PITR | Level 2: окреме резервне сховище поза кластером бази |
| Observability | Метрики, централізовані журнали, алерти | Level 2: система моніторингу, до якої надсилають дані всі контейнери |
| Interoperability | Версіоноване API, адаптери партнерів | Level 3: шар адаптерів інтеграцій між зовнішніми системами та бізнес-логікою |
| Portability | Контейнери, Infrastructure as Code | Deployment: контейнерна платформа замість сервісів, специфічних для провайдера |
| Extensibility | Інтерфейси провайдерів, адаптери каналів | Level 3: інтерфейс каналу сповіщень з окремими адаптерами SMS / push / email |

Для трьох обраних характеристик (розділ 2) ці зміни пропонується внести в модель. Для решти — ні: саме це і є прийнятим наслідком, описаним у розділі 2.4.

## 2. Вибір трьох основних характеристик

Із десяти характеристик я залишив три, які найбільше впливають на архітектуру нашого проєкту:

1. **Data Integrity** — цілісність даних.
2. **Responsiveness** — швидкість відстеження.
3. **Availability** — доступність.

Цей вибір відповідає на центральне питання для системи доставки: коли одночасно потрібні висока швидкість приймання подій і швидке відстеження, що саме має сповільнитися першим? Моя відповідь: першими можна обмежувати масові партнерські запити та відкладати некритичні сповіщення, але не можна жертвувати правильністю підтверджених статусів і платежів.

### 2.1. Чому обрано Data Integrity

Правильність інформації про посилки та платежі є критичною. Наприклад, неправильний статус може призвести до помилкової видачі посилки або неправильного рішення працівника.

Тому я вважаю, що краще тимчасово затримати операцію, ніж підтвердити некоректну зміну. Для цього використовую транзакції, перевірку версій та синхронне підтвердження записів на резервній репліці.

**Чим жертвую:** швидкістю частини операцій запису, адже підтвердження транзакції може вимагати додаткового мережевого обміну.

### 2.2. Чому обрано Responsiveness

Відстеження посилок — одна з найбільш використовуваних функцій системи.

У [ДЗ-1](../homework-1/requirements.md) для базового навантаження вже визначено 200 запитів за секунду, а для пікового — 600. Також передбачено, що 60% запитів припадає на відстеження. Отже, при піковому навантаженні система може отримувати приблизно 360 запитів відстеження за секунду.

Щоб ці запити не конкурували з усіма операціями запису, пропоную використовувати репліку бази для читання та контролювати її актуальність.

**Чим жертвую:** простотою роботи з базою даних, оскільки з'являються маршрутизація читання та необхідність контролю відставання репліки.

### 2.3. Чому обрано Availability

Для системи доставки простій впливає не лише на клієнтів, а й на роботу відділень, кур'єрів та партнерських інтеграцій. Тому потрібно уникнути ситуації, коли вихід із ладу одного сервера повністю зупиняє систему.

Пропоную використовувати декілька екземплярів Backend API та резервні вузли PostgreSQL у трьох зонах доступності.

**Чим жертвую:** вартістю та простотою інфраструктури. Додаткові сервери, реплікація та автоматичне перемикання потребують ресурсів і тестування.

### 2.4. Характеристики, які не увійшли до трійки, та прийняті наслідки

Важливо: ці характеристики не зникають із вимог системи. Я лише не роблю їх головними причинами додаткового ускладнення архітектури.

| Характеристика | Що свідомо не реалізую як пріоритет | Наслідок, який приймаю |
|---|---|---|
| Scalability | Не впроваджую необмежене автоматичне масштабування | Понад розрахований пік 600 RPS партнерські запити можуть отримувати HTTP 429 або переходити в чергу. Користувачі партнерських систем можуть чекати довше |
| Security | Не створюю окрему мережу спеціалізованих сервісів авторизації та ізоляції кожного модуля | Компрометація Backend API матиме більший потенційний вплив. Обов'язкові TLS, RBAC, MFA та перевірки доступу залишаються |
| Recoverability | Не створюю постійно активну копію всієї системи в іншому географічному регіоні | Відмова цілого регіону може вимагати відновлення з резервних копій. Залишаю попередні цілі RPO до 5 хвилин та RTO до 1 години, які ще потрібно перевірити |
| Observability | Не впроваджую повну систему розподіленого трасування всіх операцій | Пошук причини складних збоїв може тривати довше. Базові метрики, журнали та сповіщення залишаються |
| Interoperability | Не створюю універсальну платформу інтеграцій для будь-яких зовнішніх протоколів | Для нового нестандартного партнера може знадобитися окремий адаптер і додатковий цикл розробки |
| Portability | Не роблю інфраструктуру повністю незалежною від обраного хмарного провайдера | Перенесення системи до іншого провайдера стане окремим проєктом, а не простою зміною конфігурації |
| Extensibility | Не створюю окрему плагінну платформу та мікросервіс для кожної нової функції | Додавання нового каналу сповіщень або складної інтеграції може вимагати змін і повторного розгортання Backend API або Worker |

Таким чином, я свідомо надаю перевагу правильності даних, швидкості відстеження та доступності системи. Інші характеристики забезпечуються на необхідному базовому рівні без додаткового ускладнення там, де це поки не виправдано.

## 3. Quality Attribute Scenarios (QAS)

QAS — це сценарій, який описує архітектурну характеристику через конкретну ситуацію та вимірюваний результат.

Для кожної з трьох обраних характеристик я підготував один QAS за шістьма елементами: Source, Stimulus, Artifact, Environment, Response та Response Measure.

> **Важливо:** числові значення нижче — цільові показники навчальної архітектури. Частину взято з попереднього ДЗ-1, частину визначено як нові проєктні припущення. Вони ще не підтверджені реальними тестами.

### 3.1. QAS-1 — Data Integrity

| Елемент | Зміст |
|---|---|
| **1. Source — джерело** | Оператор відділення, кур'єр або партнерська система, які надсилають запити на зміну статусу посилки. |
| **2. Stimulus — стимул** | Два джерела майже одночасно надсилають зміни статусу однієї посилки. Під час обробки також може відмовити основний вузол PostgreSQL. |
| **3. Artifact — об'єкт** | Backend API, компонент керування статусами, PostgreSQL, таблиця історії та Transactional Outbox. |
| **4. Environment — середовище** | Пікове навантаження — 600 запитів за секунду. Дві конкурентні операції над однією посилкою надходять із різницею до 100 мс. Під час виконання транзакції один вузол бази даних раптово перестає працювати. |

**5. Response — реакція системи**

1. Система перевіряє дозволені переходи статусів і версію запису.
2. Лише одна з конфліктних змін може бути успішно застосована до відповідної версії.
3. Інший запит отримує HTTP 409 Conflict або, якщо це точне повторення вже виконаної операції, її збережений результат.
4. Поточний статус, історія та завдання Outbox записуються атомарно.
5. Підтверджена транзакція повинна зберігатися на синхронній резервній репліці.
6. Якщо немає можливості безпечно підтвердити запис, система не повідомляє про успішне завершення операції. Вона повертає помилку або тимчасово призупиняє запис до відновлення необхідної узгодженості.

**6. Response Measure — міра результату**

- 0 некоректних переходів статусів у тесті з 10 000 конкурентних операцій.
- 0 частково зафіксованих транзакцій.
- 0 втрачених підтверджених транзакцій у тестах відмови однієї зони за умови справної синхронної реплікації та правильного перемикання.
- Усі виявлені конфлікти повертають коректний результат без перезапису актуального стану.

**Походження чисел:** вимога атомарності та контролю версій уже була в [ADR-001](../homework-3/ADR-001.md) і [ADR-002](../homework-3/ADR-002.md). Обсяг 10 000 тестових операцій і нульова втрата підтверджених записів у визначеному сценарії відмови — запропоновані критерії приймання, які потребують перевірки.

**Висновок:** я обираю правильність даних навіть ціною тимчасової недоступності операцій запису під час критичного конфлікту або втрати безпечного кворуму.

### 3.2. QAS-2 — Responsiveness

| Елемент | Зміст |
|---|---|
| **1. Source — джерело** | Клієнт або зовнішня CRM-система, яка запитує інформацію про поточний статус посилки. |
| **2. Stimulus — стимул** | Користувач відкриває відстеження посилки під час великого навантаження, коли паралельно надходить багато нових накладних та змін статусів. |
| **3. Artifact — об'єкт** | Вебзастосунок або мобільний застосунок, Backend API, маршрут відстеження та репліка PostgreSQL для читання. |
| **4. Environment — середовище** | Пікове навантаження 600 RPS протягом 60 хвилин, з них приблизно 360 RPS — запити відстеження. Інші запити пов'язані з накладними, оплатами та операціями персоналу. Додатково відбувається масове завантаження подій від партнерських систем. Клієнт використовує мобільну мережу 4G із затримкою приблизно 100 мс. |

**5. Response — реакція системи**

1. Backend API направляє запити відстеження на придатну для читання репліку PostgreSQL.
2. Система перевіряє її відставання. Якщо репліка відстає понад 1 секунду, Backend API намагається отримати статус з основної бази.
3. Якщо навантаження продовжує зростати, система обмежує масові партнерські запити. Запити, які ще не прийнято в обробку, отримують HTTP 429 та `Retry-After`. Якщо подію надійно поставлено в чергу, партнер отримує HTTP 202 та ідентифікатор операції, а не помилкове підтвердження зміни статусу.
4. Критичні операції персоналу та відстеження зберігають вищий пріоритет.
5. Якщо актуальний статус отримати неможливо, система показує зрозумілу помилку, а не видає застарілі дані за актуальні.

**6. Response Measure — міра результату**

- При 600 RPS час відповіді API відстеження: p95 не більше 450 мс.
- 99% підтверджених змін статусу відображаються у відстеженні не пізніше ніж через 2 секунди.
- Частка помилок за пікового навантаження менше 1%.
- При перевантаженні низькопріоритетні партнерські запити обмежуються раніше, ніж погіршується обслуговування критичних операцій.
- Для клієнта зрозуміло, якщо інформація тимчасово недоступна.

**Походження чисел:** [ДЗ-1](../homework-1/requirements.md) визначає 200 RPS базового навантаження, 600 RPS пікового, 60% запитів відстеження, p95 до 300 мс на базовому навантаженні та допустиме збільшення цільового часу на 50% у пік. Звідси ціль 450 мс. Обмеження відставання репліки в 1 секунду — нове припущення для перевірки.

**Висновок:** під час перевантаження першими можуть сповільнюватися масові інтеграційні операції та некритичні сповіщення. Відстеження має залишатися швидким, а цілісність статусів — незмінною.

### 3.3. QAS-3 — Availability

| Елемент | Зміст |
|---|---|
| **1. Source — джерело** | Збій інфраструктури: відмова сервера, основного PostgreSQL або однієї зони доступності. |
| **2. Stimulus — стимул** | Одна зона доступності повністю виходить із ладу під час роботи системи. |
| **3. Artifact — об'єкт** | Балансувальник навантаження, екземпляри Backend API, кластер PostgreSQL та Notification Worker. |
| **4. Environment — середовище** | Система працює під навантаженням до 600 RPS. Backend API розгорнутий у трьох зонах доступності. PostgreSQL має один основний вузол і дві резервні репліки, а синхронне підтвердження запису вимагає щонайменше одну актуальну резервну копію транзакції. Одна із зон разом зі своїми вузлами стає недоступною без попередження. |

**5. Response — реакція системи**

1. Балансувальник виключає непрацездатні екземпляри Backend API та перенаправляє трафік на доступні.
2. Якщо відмовив основний вузол PostgreSQL, механізм перемикання визначає актуальну репліку, запобігає одночасній роботі двох основних вузлів і переводить її в роль основної.
3. На час перемикання операції запису можуть бути тимчасово призупинені. Після відновлення доступу до бази критичні операції продовжуються.
4. Якщо залишкових ресурсів недостатньо для всього пікового навантаження, система спочатку обмежує масові партнерські запити та відкладає некритичні повідомлення.
5. Notification Worker продовжує роботу на доступних вузлах, обробляючи завдання Outbox без одночасного захоплення одного завдання кількома процесами.

**6. Response Measure — міра результату**

- Доступність критичних функцій — не менше 99,9% за календарний місяць.
- Перемикання після відмови однієї зони та відновлення критичних операцій — не більше 5 хвилин.
- Після перемикання система підтримує щонайменше базове навантаження 200 RPS на критичних маршрутах.
- Підтверджені синхронно записані транзакції не втрачаються під час визначеного тесту відмови однієї зони.
- Якщо всі зони недоступні, застосовується процедура аварійного відновлення з резервних копій.

**Походження чисел:** 99,9%, 200 RPS, RPO до 5 хвилин та RTO до 1 години вже визначені в [ДЗ-1](../homework-1/requirements.md). Перемикання за 5 хвилин і підтримка базового навантаження після відмови зони — додаткові цілі, які потрібно підтвердити тестуванням. RTO до 1 години залишається окремою ціллю для важчого сценарію аварійного відновлення.

**Висновок:** система повинна переносити відмову однієї зони, але я приймаю, що в аварійному режимі її максимальна продуктивність може бути меншою. Пріоритет надається критичним операціям, а не однаковій швидкості всіх функцій.

## 4. Перегляд ADR та C4-моделі

Після вибору трьох головних характеристик я повторно проаналізував попередні архітектурні рішення та схеми.

Виявилося, що наявна модель уже враховує частину необхідних механізмів, але недостатньо показує розподіл навантаження та відмовостійкість інфраструктури.

### 4.1. Що змінюється на C4 Level 1

На першому рівні змін не потрібно.

System Context показує користувачів, головну систему та зовнішні сервіси. Реплікація, балансування й резервні вузли — це внутрішні архітектурні механізми. Вони не змінюють зовнішні межі системи.

### 4.2. Що змінюється на C4 Level 2

Другий рівень потребує уточнення способу розгортання основних контейнерів.

**Було:**

- Один логічний Backend API.
- Один логічний PostgreSQL.
- Окремий Notification Worker.

**Пропоную додати:**

1. Балансувальник навантаження перед Backend API.
2. Три екземпляри Backend API у різних зонах доступності.
3. Основний вузол PostgreSQL та дві резервні репліки.
4. Використання актуальної репліки для запитів відстеження.
5. Механізм автоматичного перемикання бази даних.
6. Декілька екземплярів Notification Worker.

Важливо, що три екземпляри Backend API — це не три різні контейнери з різною бізнес-логікою, а три запущені копії одного контейнера.

Тому в C4 Container Diagram залишаю один логічний Backend API з позначенням реплікації, а фізичне розміщення вузлів за зонами за потреби показую окремою Deployment Diagram. Це дозволить відобразити нову інфраструктуру без порушення правил C4.

### 4.3. Що змінюється на C4 Level 3

Третій рівень деталізує внутрішню структуру Backend API. Для підтримки швидкого відстеження пропоную логічно розділити компонент роботи зі статусами на дві відповідальності:

1. **Tracking Query — читання статусів.** Відповідає за отримання інформації про поточний стан посилки, вибір джерела читання та перевірку актуальності репліки.
2. **Status Command — зміна статусів.** Відповідає за перевірку дозволених переходів, контроль версій і виконання транзакцій.

При цьому Status Command залишається пов'язаним із PostgreSQL, історією змін та Outbox.

Платіжний модуль, авторизація, партнерські інтеграції та інші компоненти можуть залишитися в попередній структурі.

### 4.4. Перегляд ADR-001

[ADR-001](../homework-3/ADR-001.md) визначає зберігання поточного статусу разом з історією змін.

Початкове рішення залишається правильним. Воно відповідає обраній характеристиці Data Integrity.

Однак тепер потрібно додатково визначити, як забезпечити збереження підтверджених транзакцій під час відмови головного вузла PostgreSQL. Це оформлено новим [ADR-004](ADR-004.md) щодо синхронної реплікації та перемикання бази даних, без переписування вже прийнятого рішення.

### 4.5. Перегляд ADR-002

[ADR-002](../homework-3/ADR-002.md) визначає контроль переходів статусів і захист від одночасних змін.

Рішення залишається актуальним. Optimistic Locking і перевірка дозволених переходів потрібні незалежно від кількості запущених екземплярів Backend API.

Однак після додавання резервних вузлів PostgreSQL потрібно окремо перевірити, що перемикання основного вузла не призводить до втрати підтвердженої версії запису. Також важливо не допускати одночасної роботи двох основних вузлів бази даних після мережевого розділення.

### 4.6. Перегляд ADR-003

[ADR-003](../homework-3/ADR-003.md) визначає асинхронне надсилання повідомлень через Notification Worker та Transactional Outbox.

Рішення залишається актуальним. Під час перевантаження повідомлення можуть оброблятися пізніше, не блокуючи зміну статусу.

Якщо запускаємо декілька екземплярів Notification Worker, потрібно додати механізм безпечного захоплення завдань. Наприклад, PostgreSQL може використовувати `FOR UPDATE SKIP LOCKED`, щоб два Worker не брали в роботу один і той самий запис одночасно.

При цьому повторне надсилання все одно можливе після певних збоїв, тому ідемпотентність залишається необхідною.

### 4.7. Нові архітектурні рішення

На основі перегляду C4 та попередніх ADR я зафіксував два додаткові архітектурні рішення:

1. [ADR-004 — Реплікація PostgreSQL та автоматичне перемикання при відмові](ADR-004.md). Визначає кількість реплік, синхронне підтвердження транзакцій, порядок перемикання та поведінку системи під час втрати кворуму.
2. [ADR-005 — Розділення читання та запису для відстеження посилок](ADR-005.md). Визначає використання репліки для читання, допустиме відставання, маршрутизацію запитів і пріоритети під час перевантаження.

Попередні три ADR не потрібно переписувати, оскільки вони залишаються обґрунтованими.

### 4.8. Загальний підсумок змін

Після аналізу архітектурних характеристик я визначив, що початкова архітектура добре розділяє бізнес-функції, але потребує уточнення способів забезпечення доступності та швидкого читання.

Основні запропоновані зміни:

1. Додавання резервних екземплярів Backend API.
2. Реплікація PostgreSQL між зонами доступності.
3. Автоматичне перемикання при відмові основного вузла.
4. Розділення шляхів читання та запису статусів.
5. Пріоритизація критичних операцій при перевантаженні.
6. Можливість запускати декілька Notification Worker.
7. Додаткові перевірки узгодженості під час перемикання бази.

На першому рівні C4 змін не потрібно. Основні зміни стосуються другого рівня, розгортання інфраструктури та окремих компонентів третього рівня.

Описані зміни є архітектурними пропозиціями за результатами цього завдання. Їх необхідно внести в редаговану [C4-схему](../homework-2/C4_1-3_Levels.drawio) перед тим, як вважати оновлення моделі завершеним.

## 5. Загальний висновок

Для навчального проєкту «Нова пошта» я розглянув десять архітектурних характеристик і визначив три головні: цілісність даних, швидкість відстеження та доступність.

Кожна з них впливає на структуру системи й потребує конкретних механізмів реалізації:

- **Цілісність даних** забезпечується транзакціями, контролем версій і синхронною реплікацією.
- **Швидкість відстеження** забезпечується розділенням операцій читання та запису, контролем актуальності реплік і пріоритизацією запитів.
- **Доступність** забезпечується резервними екземплярами Backend API, розміщенням у кількох зонах і можливістю автоматичного перемикання бази даних.

Водночас я свідомо приймаю додаткову складність інфраструктури, вищу вартість підтримки й обмеження продуктивності окремих другорядних операцій під час перевантаження.

Головний висновок полягає в тому, що архітектура повинна не просто підтримувати якомога більше характеристик, а відображати свідомий вибір пріоритетів та наслідків цього вибору.
